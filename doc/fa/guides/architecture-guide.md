# راهنمای معماری

یک مخزن چگونه به بخش‌ها تقسیم می‌شود و این بخش‌ها چگونه رشد می‌کنند.
[راهنمای کد](./code-guide.md) قواعد یک فایل و یک تابع را در بر دارد؛ این
راهنما قواعد بالاتر از آن‌ها را. ساختار را همان‌طور شکل بده که یک توسعه‌دهندهٔ
ارشد می‌دهد: از جایی که پروژه به سمتش می‌رود، نه فقط از آنچه امروز انجام
می‌دهد.

## از جایی که پروژه به سمتش می‌رود شروع کن <a id="start-from-where-the-project-is-going"></a>

- دریاب مخزن چه نقشی دارد: یک دامنه (domain) را در خود دارد، CLI یا
  لایهٔ اتصال (glue) روی دامنه‌ای است که جای دیگری نگه داشته می‌شود،
  کتابخانه‌ای با مصرف‌کنندگان است، یا از مخزن دیگری پیروی می‌کند (port،
  آینه، fork، کد تولیدشده). مخزنی که از دیگری پیروی می‌کند با این سنجیده
  می‌شود که چقدر ارزان می‌تواند به پیروی ادامه دهد؛ تغییرات ساختاری در API
  آینه‌شده اول جایشان در upstream است. در یک مخزن پیرو، ساختاری که با
  upstream جور است یافته نیست؛ انحراف از upstream یافته است
- اهداف را پیش از کد بخوان: مخزن مدیریت پروژه (اهداف، نیازمندی‌ها، معماری
  فصل جاری) اگر وجود دارد، مفهوم در `CLAUDE.md`، README، تیکت‌های باز
  (پوشه‌های تیکت فضای کاری با `ticket.json` آن‌ها، که فقط تا وقتی شاخه‌شان
  merge نشده باز هستند، و issueهای میزبان مخزن) و `git log`. CHANGELOG را
  به‌عنوان مسیری که کار گذشته پیموده بخوان، نه فهرستی از اهداف
- این‌که سیستم کجا تغییر خواهد کرد را فقط از شواهدی استنتاج کن که بتوانی
  نامشان را ببری: یک interface با یک پیاده‌سازی که منتظر بیشتر است، بخشی از
  README دربارهٔ گسترش آن، فایل‌هایی که تاریخچه نشان می‌دهد با هر قابلیت تغییر
  می‌کنند، مصرف‌کننده‌ای که دور آنچه دریافت می‌کند راه‌حل می‌سازد، یک تیکت
  باز، یا آنچه کاربر می‌گوید. محوری بدون شاهد هیچ توصیه‌ای ندارد؛ حداکثر به
  یک پرسش از کاربر تبدیل می‌شود
- ویژگی‌های کیفی‌ای را که در این‌جا درباره‌ی بده‌بستان‌ها تصمیم می‌گیرند نام ببر،
  فقط آن‌هایی که منابع یا کد نشان می‌دهند: پلتفرم‌های هدف در manifest یا CI،
  بنچمارک‌ها، خروجی‌های ذخیره‌شده، اصلاحات نسخه‌های اخیر. بررسی کن که هیچ API
  وابسته به پلتفرمی جلوی یک پلتفرم هدفِ نام‌برده را نگیرد
- آنچه منابع می‌گویند را از آنچه خودت استنتاج می‌کنی جدا نگه دار؛ هدفِ
  استنتاج‌شده تا وقتی کسی تأییدش نکند یک فرضیه است
- اگر هیچ منبعی برای اهداف نیست، همین را بگو؛ آن‌گاه تصویر هدف، ساختار
  فعلی است به‌اضافهٔ اصلاح آنچه همین امروز هزینه دارد

## در امتداد مفهوم‌ها برش بزن <a id="cut-along-concepts"></a>

- یک مفهوم برای هر ماژول، یک مفهوم سطح بالا برای هر بسته؛ ماژول را وقتی
  تقسیم کن که مفهوم‌هایش کاربران متفاوتی دارند یا با سرعت‌های متفاوتی تغییر
  می‌کنند، نه به‌خاطر اندازه‌اش
- ماژول را به نام مفهومی که در خود دارد نام‌گذاری کن، هرگز به نام تکنیکش
  (`helpers`، `utils`، `misc`، `common`)
- بگذار وابستگی‌ها در یک جهت اشاره کنند: از لبه‌ها (UI، CLI، IO، شبکه،
  فریم‌ورک) به سمت هسته‌ای که دامنه را در خود دارد
- ابتدا دریاب کدام بسته دامنه را در خود دارد؛ آن هسته را از نوع‌های IO، UI و
  فریم‌ورک پاک نگه دار. یک بستهٔ CLI یا glue روی دامنه‌ای که جای دیگری است،
  هستهٔ خودش را ندارد
- هیچ چرخه‌ای میان ماژول‌ها یا بسته‌ها مجاز نیست

## درون را پنهان کن <a id="hide-the-inside"></a>

- API عمومی را کوچک نگه دار؛ هر چیزی که فراخواننده لازم ندارد خصوصی است
- به هر بخش از وضعیت دقیقاً یک مالک بده؛ دیگران از مالک می‌پرسند، به‌جای
  این‌که به داده‌هایش دست ببرند
- مقادیر تغییرناپذیر تحویل بده، نه ارجاع به مجموعه‌های درونی
- ساعت، IO، تصادفی‌بودن و محیط را جایی تزریق کن که کد در غیر این صورت روی
  یک پرچم تست یا یک متغیر محیطی شاخه می‌زد
- یک کتابخانهٔ شخص ثالث را فقط جایی پشت interface خودت پنهان کن که اهداف
  جایگزینی آن را نام می‌برند یا API آن مدام تغییر می‌کند و به ماژول‌های
  زیادی نشت می‌کند؛ نه برای بسته‌های خود سازمان یا مبانی پایدار مانند path
  یا args

## API عمومی و خروجی‌های ذخیره‌شده را تعهد بدان <a id="treat-the-public-api-and-stored-outputs-as-promises"></a>

- برای یک بستهٔ منتشرشده، API عمومی مهم‌ترین مرز است؛ پیش از داوری یا تغییر
  آن، مصرف‌کنندگانش را پیدا کن (`interfaces.usedBy` در `index.jsonc`،
  importها در سراسر `.ocean`، re-exportها)
- API عمومی‌ای که کسی از آن استفاده نمی‌کند، و API عمومی‌ای که فقط برای تست‌ها
  وجود دارد، وقتی همهٔ مصرف‌کنندگان شناخته شدند یافته‌اند؛ برای بسته‌ای که
  بیرون از فضای کاری منتشر شده، مصرف‌کنندگان بیرونی را فرض کن و بپرس
- خروجی‌هایی که ذخیره یا ارسال می‌شوند (مقادیر hash، قالب‌های فایل، خروجی CLI
  که اسکریپت‌ها تجزیه می‌کنند) هم قرارداد هستند؛ پیش از بازسازی ساختار،
  آن‌ها را با تست‌های golden تثبیت کن
- آنچه مصرف‌کنندگان استفاده می‌کنند یک قرارداد است؛ آنچه نیاز دارند و خودشان
  از نو می‌سازند یک هدف است

## هر مفهوم را یک بار بگو <a id="say-each-concept-once"></a>

- یک ایدهٔ واحد که در دو ماژول پیاده شده، یک مفهومِ غایب است؛ به آن خانه‌ای
  بده و بگذار هر دو از آن استفاده کنند
- از نو ساختن آنچه یک وابستگی یا یک مخزن هم‌سطح از قبل ارائه می‌کند،
  تکرار در میان مخزن‌هاست؛ از نسخهٔ آن‌ها استفاده کن، یا یکی را تنها خانهٔ آن
  کن. دو پیاده‌سازی از یک مفهوم که نتایج متفاوت می‌دهند، یک نقص‌اند
- به یک بخش مشترک، در دومین مصرف‌کننده، ماژولی از آنِ خودش بده. وقتی
  مصرف‌کننده‌ای در مخزن دیگری به آن نیاز دارد، آن را به مخزن موجودی منتقل کن
  که دامنه‌اش جور است؛ فقط وقتی هیچ‌کدام جور نیست بستهٔ تازه بساز و هزینه‌اش
  را نام ببر: زنجیرهٔ انتشار، نسخه‌ها، توزیع DNA (DNA rollout)
- دو جایی که برای هر قابلیت تازه با هم تغییر می‌کنند، یک مفهوم‌اند که دو
  تکه شده
- هر شباهتی تکرار نیست: دو تکه که شبیه هم‌اند ولی به دلایل متفاوتی تغییر
  می‌کنند جدا می‌مانند؛ همین‌طور کدی که برای سرعت تخصصی شده، وقتی یک بنچمارک
  یا دلیلی بیان‌شده در کد پشتیبانش است

## با افزودن رشد کن، نه با ویرایش <a id="grow-by-adding-not-by-editing"></a>

- جایی که اهداف تغییرپذیری را پیش‌بینی می‌کنند، کوچک‌ترین درزی (seam) را
  بگذار که آن را حمل کند: یک پارامتر تابع یا یک جدول داده پیش از یک
  interface، یک interface پیش از یک registry
- نوع تازه‌ای از چیزها را به شکل نوع تازه‌ای اضافه کن که interface را برآورده
  می‌کند، به‌جای شاخه‌ای تازه در هر `switch` روی انواع
- این برای انواعی صدق می‌کند که اهداف انتظار رشدشان را دارند؛ یک `switch` روی
  مجموعه‌ای بسته (نوع‌های یک زبان، انواع مقدار یک قالب مانند JSON، یک
  پروتکل ثابت) همان `switch` می‌ماند
- درز را همان‌جا نگه دار که تغییرپذیری هست، نه یک سطح بالاتر یا پایین‌تر
- رفتار را از طریق داده پیکربندی کن، جایی که گونه‌ها فقط در مقادیر تفاوت
  دارند

## برای آینده‌های خیالی نساز <a id="do-not-build-for-imagined-futures"></a>

- یک تغییر ساختاری جایگاهش را با یک هدف از `@goals` به دست می‌آورد یا با
  هزینه‌ای که امروز وجود دارد و می‌توانی نشانش دهی: فایلی که تاریخچه نشان
  می‌دهد با هر قابلیت تغییر می‌کند، کپی‌هایی که از هم فاصله گرفته‌اند، باگی که
  ساختار باعثش شده. ارزان نگه داشتن تغییرِ یک نقطهٔ داغ (hotspot) وقتی
  تاریخچه نشان می‌دهد کار آن‌جا ادامه دارد، یک هدف به حساب می‌آید. بدون هیچ‌کدام،
  ساختار را همان‌طور که هست رها کن
- هر درز به هدفی پشت خود نیاز دارد؛ انتزاعی با تنها یک پیاده‌سازی و بدون
  هدفی که دومی را بخواهد، یک یافته است
- ساده‌ترین ساختاری را که اهداف را حمل می‌کند بر کلی‌ترین ساختار ترجیح بده
- فریم‌ورک‌های عمومی درون یک برنامه، لایه‌هایی که فقط فراخوانی‌ها را عبور
  می‌دهند و گزینه‌هایی که کسی تنظیمشان نمی‌کند، هزینه‌ای بی‌بازده‌اند

## پیش از نوشتن، تصمیم بگیر کد تازه کجا می‌رود <a id="decide-where-new-code-goes-before-you-write-it"></a>

- تصویر هدفِ ثبت‌شده را، اگر پروژه دارد، بخوان و کد را همان‌جا بگذار که
  می‌گوید
- پیش از افزودن به یک فایل یا کلاس موجود، بپرس آیا قابلیت به مفهومی که آن
  در خود دارد تعلق دارد؛ اگر نه، به آن ماژول یا نوعی از آنِ خودش بده
- وقتی در آستانهٔ گسترش یک `switch` روی انواع، افزودن یک پرچم حالت یا کپی
  کردن یک بلوک هستی، مفهوم غایب را نام ببر و به‌جای آن، آن را اضافه کن
- پیش از نوشتن، مفهوم را در این مخزن، وابستگی‌هایش و مخزن‌های `.ocean`
  جست‌وجو کن (ببین `@dry`)
- وقتی جای درست ابتدا به تغییری ساختاری نیاز دارد، یا در مخزن دیگری است،
  آن را پیشنهاد کن و پیش از نوشتن بپرس

## مراقب ساختاری باش که با انباشت رشد کرده <a id="watch-for-structure-that-grew-by-accretion"></a>

کدی که قابلیت به قابلیت رشد کرده، به‌ویژه به دست یک عامل (agent)، تمایل دارد
رفتار تازه را به آنچه از قبل هست پیچ کند. به دنبال این‌ها بگرد:

- کلاس یا فایلی که با هر قابلیت بزرگ‌تر می‌شود و از همه چیز کمی می‌داند
- یک `switch` یا زنجیرهٔ `if` روی نوعی که انتظار رشدش می‌رود، که در چند جا
  تکرار شده
- پارامتر بولی یا حالتی که یک تابع را به دو تابع تبدیل می‌کند
- یک ماژول کامل که به‌جای اشتراک، کپی و کمی تغییر داده شده
- کد UI یا CLI که مستقیماً از ذخیره‌ساز، شبکه یا فایل‌ها می‌خواند
- وضعیت تغییرپذیر مشترکی که چند ماژول در آن می‌نویسند، مانند پرچم‌ها و
  شمارنده‌های ایستا، به‌جای وضعیتی که متعلق به یک زمینهٔ (context) صریح است
- کاری که هنگام import شدن یک ماژول انجام می‌شود
- قلاب‌های تست (test hook) در API عمومی، یا شاخه‌زدن روی `isTest` یا
  متغیرهای محیطی در کد کتابخانه
- یک ماژول زباله‌دانی که همه import می‌کنند
- فایل‌هایی که در بیشتر commitهای قابلیت با هم تغییر می‌کنند، بدون احتساب
  تست‌ها، manifestها، changelogها و barrelها؛ نشانه‌ای برای دقیق‌تر خواندن،
  نه هنوز یک حکم

## ساختار را در گام‌های کوچک تغییر بده <a id="change-the-structure-in-small-steps"></a>

- ابتدا تصویر هدف را ترسیم کن، سپس راه رسیدن به آن را برنامه‌ریزی کن
- هر گام را قابل تحویل کن: تست‌ها سبز می‌مانند و نسخهٔ انتشار پس از هر گام کار
  می‌کند
- رفتاری را که تست‌ها پوشش نمی‌دهند، پیش از یک گام ساختاری با تست‌های
  توصیفی (characterisation) یا golden تثبیت کن؛ هر جا ممکن است تست‌ها را با
  کد جابه‌جا کن، و جایی که تست‌ها خروجی CLI یا متن لاگ را assert می‌کنند،
  هزینهٔ بازنویسی را نام ببر
- ساختار تازه را کنار ساختار قدیمی بگذار، فراخوانندگان را منتقل کن، سپس
  قدیمی را حذف کن
- ساختار و رفتار را در گام‌های جداگانه تغییر بده، هرگز در یک commit
- هر گام را شکننده (breaking) یا ناشکننده دسته‌بندی کن؛ وقتی ممکن است
  مصرف‌کنندگانی بیرون از فضای کاری وجود داشته باشند، پیش از حذف آن را منسوخ
  (deprecated) اعلام کن و حذف‌ها را در یک نسخهٔ major دسته کن؛ وقتی همهٔ
  مصرف‌کنندگان در فضای کاری‌اند، آن‌ها را در همان تیکت فضای کاری به‌روز کن
- گام‌هایی را که چند مخزن را در بر می‌گیرند بر اساس زنجیرهٔ انتشار مرتب کن،
  اول بستهٔ ارائه‌دهنده، به‌صورت یک تیکت فضای کاری
- تصویر هدف را همان‌جا ثبت کن که پروژه نگهش می‌دارد، تا تغییر بعدی از آن
  پیروی کند
