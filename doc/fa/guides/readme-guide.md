# راهنمای README

برای README یک بسته (package) یا یک اپ این راهنما را دنبال کنید. یک مخزن
DNA — لایه‌ای که مخزن‌های دیگر آن را در `dna/_dna.json` خود فهرست می‌کنند
— برای بخش‌هایش از [راهنمای README برای DNA](./readme-dna-guide.md) پیروی
می‌کند؛ قواعد زیر دربارهٔ سبک، زبان‌ها و بررسی برای آن هم برقرارند.

## کپی کردن قالب <a id="copy-the-template"></a>

- `doc/en/templates/readme-template.md` را در `README.md` کپی کنید، یا
  README موجود را بر اساس آن بازبینی کنید
- ترتیب بخش‌ها را حفظ کنید و بخش‌های اختیاری‌ای را که مخزن چیزی برایشان
  ندارد حذف کنید
- هر `<placeholder>` را جایگزین کنید

## با کاری که انجام می‌دهد شروع کنید <a id="open-with-what-it-does"></a>

- نام، نشان‌ها (badges) و یک یا دو جمله را در صفحهٔ اول بگذارید — خواننده
  همان‌جا تصمیم می‌گیرد که بسته به کارش می‌آید یا نه
- `description` در `pubspec.yaml` یا `package.json` را همان جمله قرار
  دهید تا GitHub، pub.dev و npm یک چیز بگویند
- محدودیت‌های سخت را زود نام ببرید، مثلاً پلتفرم‌های پشتیبانی‌شده

## بگویید چرا وجود دارد <a id="say-why-it-exists"></a>

- انگیزه را بنویسید: مشکل یا اصطکاکی که به ساخت مخزن انجامید، و هدفی که
  دنبال می‌کند
- آن را برای تازه‌وارد بنویسید — «چرا» چیزی است که READMEها بیش از همه
  جا می‌اندازند
- آن را از مخزن، مستنداتش و تاریخچه‌اش بردارید؛ اگر چیزی نمی‌گویند از
  کاربر بپرسید، هرگز آن را از خود نسازید

## نشان دهید که کار می‌کند <a id="show-it-working"></a>

- برای هر اکوسیستم یک فرمان نصب قابل کپی بدهید
- مهم‌ترین قابلیت را به صورت قطعه‌کدی (snippet) نشان دهید که بدون تغییر
  اجرا شود — بدون شبه‌کد، بدون TODO
- قطعه‌کد را با کد `example/` یکسان نگه دارید؛ pub.dev آن فایل را در زبانهٔ
  Example نشان می‌دهد
- نشان دهید قطعه‌کد چه چیزی چاپ می‌کند

## بگویید کجا تمام می‌شود <a id="say-where-it-ends"></a>

- آنچه بسته عمداً انجام نمی‌دهد و نقاط حساسش را نام ببرید
- میزان پختگی را بیان کنید، مثلاً اینکه API ممکن است پیش از 1.0 تغییر کند

## پیوند دهید به جای تکرار <a id="link-instead-of-repeating"></a>

- راهنماها، مستندات معماری و بلاگ را پیوند دهید؛ آن‌ها را کپی نکنید
- فقط به فایل‌هایی پیوند دهید که در مخزن وجود دارند
- متن پیوند را طوری بنویسید که بگوید به کجا می‌رود، هرگز «اینجا»

## نشان‌ها کم و درست <a id="keep-badges-few-and-true"></a>

- حداکثر پنج تا: CI، نسخهٔ رجیستری، امتیاز pub، پوشش (coverage)، مجوز
- نشان CI را به یک فایل workflow در `.github/workflows/` ارجاع دهید
- نشانی را که کسی وضعیتش را دنبال نمی‌کند حذف کنید

## Markdown ساده بنویسید <a id="write-plain-markdown"></a>

- برای عنوان‌ها حالت جمله‌ای (sentence case) و برای کارها حالت امری به کار
  ببرید، مثلاً «بسته را نصب کنید»
- زبان هر بلوک کد را مشخص کنید
- فقط پیوندهای `https` — pub.dev برای `http` امتیاز کم می‌کند
- فهرست مطالب اضافه نکنید، GitHub خودش یکی می‌سازد

## آن را به همهٔ زبان‌های مخزن بنویسید <a id="write-it-in-every-language-of-the-repo"></a>

- زبان‌های این مخزن، با زبان اصلی در ابتدا، `en` هستند
- `README.md` را به انگلیسی نگه دارید و برای هر زبان دیگر یک
  `README.<lang>.md` داشته باشید، مثلاً `README.de.md`، `README.fa.md`
- زیر عنوان یک انتخابگر زبان بگذارید که همهٔ زبان‌ها را نام ببرد و به
  همهٔ زبان‌های دیگر پیوند دهد، مثلاً `English | [Deutsch](README.de.md)`
  در `README.md` و `[English](README.md) | Deutsch` در `README.de.md`
- همه را از نظر محتوا و ساختار یکسان نگه دارید: همان بخش‌ها با همان
  ترتیب، عنوان‌ها و متن ترجمه‌شده
- بلوک‌های کد را، همراه با توضیحاتشان، یکسان نگه دارید
- README را ابتدا به زبان اصلی بنویسید، سپس ترجمه کنید
- از `doc/en/guides/translate-guide.md` پیروی کنید
- pub.dev و npm فقط `README.md` را نشان می‌دهند

## آن را بررسی کنید <a id="check-it"></a>

- `node scripts/check-readme.js` را اجرا کنید؛ این اسکریپت این موارد را
  گزارش می‌کند: عنوانی که نام بسته نیست، بخش‌های جاافتاده یا نابه‌جا،
  جای‌نگهدارهای باقی‌مانده، پیوندها و نشان‌های خراب، نشان‌های بیش از حد،
  بلوک‌های کد بدون زبان، جمله‌ای که با `description` فرق دارد، و README
  آلمانی‌ای که از اصل فاصله گرفته است
- README را در همان تغییری به‌روز کنید که کدِ توصیف‌شده در آن تغییر می‌کند
